0. 项目背景与现状

当前 GKI 升级与修改合入内部时，普遍存在以下问题：

  • 审阅成本高：单笔 patch 与整段 tag 区间体量大，人工逐笔分析难以稳定覆盖风险点、测试建议与合入策略。
  • 口径不统一：不同评审人对「是否可合入、需补哪些测试」判断不一致，难以沉淀为可复用的规则与证据链。
  • 可追溯性弱：合入决策缺少结构化记录（分数、维度、依据、建议测试项），不利于审计、复盘与跨版本对比。

建设 GKI PATCH 工具，以自动化方式从官方仓库拉取 commit 元信息与 diff 信号，针对代码修改输出结构化评分与报告，可显著降低代码审阅工作量，降低合入风险与沟通成本，符合 GKI 长期维护与快速安全响应的现实需求。

1. 工具概述

gkiPatchTool 是一个面向 Android GKI（Generic Kernel Image）内核补丁的批量分析与可视化报告工具。它能够从 Android Kernel 公共仓库（android.googlesource.com）抓取指定版本区间内的所有提交（commit），逐笔进行多维评分分析，并生成结构化报告，帮助内核开发/集成人员快速评估 Patch 的风险等级、测试建议和影响范围。

工具分为两套使用方式：

🔧 CLI 模式

本地命令行独立运行，支持区间分析、单 SHA 分析、采样分析。适用深度分析、批量导出和 CI/CD 自动化脚本集成。无任何 GUI 依赖。

🌐 Web 模式

基于 FastAPI 的交互式平台，通过浏览器即可操作。支持任务管理、实时进度推送、可视化报告、死机分析和数据库浏览等功能。

2. 核心功能详解

2.1 补丁分析引擎（CLI）

核心分析器 patch_analyzer.py（≈2900行）实现了一套完整的补丁分析管线，支持从远程仓库或本地 Git 仓库获取数据并执行多维评分。

分析模式

模式命令参数说明
区间分析--from-tag <TAG> --to-tag <TAG>分析两个 Git tag 之间的全部 commit
单 SHA 分析--commit <SHA>分析单个 commit
采样分析Web 页面设置 sample_size区间过大时按比例采样快速评估

可配置参数（CLI）

参数默认值说明
--repo（必填）仓库 URL，如 https://android.googlesource.com/kernel/common
--config（必填）评分规则 YAML 配置文件路径
--workers6并行分析线程数，控制 API 并发请求量
--chunk-size100每批处理的 commit 数量，大区间建议 50~100
--retry1每个 commit 分析失败时的重试次数
--repo-dir（可选）本地 Git 仓库路径，可避免远程 API 速率限制
--outputpatch-analysis-result.json分析结果 JSON 输出路径

多维评分体系

每个 patch 从以下维度进行评分（每项 0-10 分，加权求和）：

维度默认权重评分依据
correctness_completeness
（正确性与完整性）		配置驱动commit message 是否包含 fix/bug 信号、修改文件数、代码改动量（churn）
risk_safety
（风险与安全性）		配置驱动是否涉及高风险路径（mm/security/kernel/arch/fs）、改动量
testability_evidence
（可测性与证据）		配置驱动是否包含测试信号（selftest/kunit 等）
diff_maintainability
（代码可维护性）		配置驱动按文件数和改动量线性扣分
commit_metadata_quality
（提交元数据质量）		配置驱动commit message 质量、是否包含 Fixes/Signed-off-by 等标记

风险信号评分扩展

YAML 配置中的 risk_signal_score_rules 允许定义自定义风险信号规则（如检测 CVE 编号、特定内存操作模式等），自动注入对应维度的加分/扣分。

标签自动分类

工具自动识别并打上两类标签：

  • 路径标签（patch_tags）：根据修改文件路径识别子系统（包括：内存管理、文件系统、网络协议栈、安全、加密、调度、锁/并发、BPF、电源管理、DRM/图形、USB、Android/GKI 等 25+ 类）
  • 意图标签：基于 commit message 启发式推断 patch 意图（fix bug / 新需求）
  • 平台标签（platform_tags）：识别涉及的 CPU 架构（ARM64/ARM/x86/RISC-V/LoongArch 等）
  • 开发模块标签（dev_module）：基于 21 个标准开发模块的路径映射规则分类

引入追溯（Introducer Analysis）

当检测到 patch 包含 fix/regression 等修复信号时，自动追溯问题引入的原始提交。通过本地 Git 历史在同文件/同函数范围内检索，基于修改文件重合度、函数名匹配、代码形态相似度等多维特征打分，找出最可能的引入修改。

输出内容结构

每个 patch 的分析结果包含：

字段说明
score综合评分（0-10）
score_details各维度评分明细（含 base_score、applied_rules、additions、deductions）
why_scored打分关键依据列表
recommendation推荐结论（建议合入/有条件合入/需大幅修改/不建议合入）
key_risk核心风险描述
test_suggestions建议测试项（单元测试/集成测试/回归测试/手工验证/发布保障）
patch_tags子系统标签列表
platform_tags架构平台标签列表
dev_module所属开发模块
blocked是否触发硬阻断
block_rules_hit触发的阻断规则列表
introducer_analysis问题引入追溯结果（含 detected、confidence、introducer_commit、evidence）

2.2 Web 交互平台

基于 FastAPI + SQLite + WebSocket 的轻量 Web 应用，全栈纯 Python + 原生 JavaScript 实现，无需任何前端框架。

任务管理

  • 创建任务：通过页面表单提交区间分析（指定 from_tag/to_tag/sample_size）或单 SHA 分析
  • 任务列表：展示最近 200 条任务，包含状态（pending/running/completed/failed）、类型、区间、进度百分比
  • 任务详情：点击查看单任务下所有 patch 的分析结果卡片
  • 模块筛选：按 21 个开发模块过滤当前任务下的 patch
  • 删除任务：支持单条删除和批量删除，删除任务不影响已保存的 patch 分析数据

实时进度跟踪

  • 三阶段进度条：collecting → analyzing → llm_analyzing（或双阶段）
  • WebSocket 长连接：每秒推送最新进度，前端实时更新阶段名称、百分比、已用时间
  • 基于完成数量：进度 = 已处理 commit 数 / 总 commit 数，非时间驱动，准确反映真实进度
  • 任务取消：一键标记取消，运行中的线程检测到取消标记后自行停止

LLM 配置管理

  • 页面内配置：支持设置 API Key、API Base URL、Model 名称
  • 分层覆盖：环境变量 → 数据库（页面配置优先级高于环境变量）
  • 环境变量支持：GKI_LLM_API_KEY、GKI_LLM_API_BASE、GKI_LLM_MODEL
  • 自动切换分析流程：配置 LLM 后，分析流程自动跳过脚本分析阶段，直接进入 LLM 分析

2.3 LLM 深度分析

集成了 LLM 多维度分析能力，提供比脚本评分更深入的代码理解。

单笔 Patch LLM 分析

  • 逐笔调用 LLM 对 patch 进行深度审查
  • 输出 commit_interpretation_rich：对修改意图的人工解读
  • 输出 problem_closure_rich：问题修复类型和风险等级评估
  • 输出 LLM 评分：各维度评分与理由，与脚本评分交叉验证
  • 输出 LLM test_suggestions：基于代码理解的测试建议
  • 记录 token 消耗（usage 字段），方便追踪 API 费用

区间 Squash Diff 总结

  • 对整个区间合并 diff 调用 LLM 生成全面的技术总结报告
  • 包含：变更概述、主要变更领域、风险评估、影响范围
  • 分模块详细总结：按 21 个开发模块对每个模块的具体修改做详细说明
  • 测试建议：针对整个区间的综合测试建议

双模流程

条件执行流程
已配置 LLMcollecting → llm_analyzing（跳过脚本分析）
未配置 LLMcollecting → analyzing（仅脚本分析）
脚本分析完成后手动触发analyzing → llm_analyzing（追加 LLM 分析）

2.4 死机分析（Crash Analysis）

针对 GKI 升级场景中的内核死机问题定位，提供端到端的分析流程。

两阶段流程

阶段说明
Phase 1: 疑似 Patch 检索用户输入内核死机日志（Kernel Panic / Oops），系统提取关键特征（crash_files、crash_symbols、crash_function 等），在区间 commit 中检索并排序疑似 patch
Phase 2: 归因分析在疑似 patch 基础上，检查后续提交中是否有修复代码（revert、bug fix），识别间接因果关联，最终由 LLM 生成综合归因报告

核心能力

  • LLM 日志分析：自动识别死机类型（panic/oops/NULL pointer dereference/uaf 等）、崩溃函数、模块、调用栈链路
  • 多维度匹配：基于文件路径、函数名、符号名、死机机制描述等多维特征评分
  • 间接因果识别：通过 LLM 分析后续提交的 commit message 和 diff，判断是否存在关联修复
  • 疑似 Patch 增强：每个疑似 patch 支持折叠展示 commit 信息 + Diff 全文
  • 历史记录：每次分析保存为独立记录，支持查阅、删除和报告下载

2.5 报告生成与导出

提供 6 种报告渲染/导出工具，满足不同场景需求：

工具输入输出适用场景
render_report.py分析结果 JSON交互式 HTML标准报告，支持评分明细折叠/Diff 展示
render_report_indexed.py分析结果 JSON索引式 HTML大量 patch 时带索引导航
render_report_llm.py分析结果 JSONLLM 增强 HTML集成 LLM 分析结果（commit 解读、归因）
render_interval_hybrid_overview.py分析结果 JSON区间概览 HTML多区间对比概览
export_patch_analysis_to_excel.py分析结果 JSONExcel xlsx数据进一步加工/分享
Web 在线下载数据库HTML 报告Web 端直接下载单任务完整报告

2.6 全量合并 Diff

分析任务完成后，自动生成所选版本区间内全部 Patch 的合并 Diff 文件（保存至 outputs/merged_diffs/），可通过 Web 页面在线下载。生成失败不影响主分析任务状态。

2.7 数据库浏览

提供独立的数据库浏览页面（/patches），支持：

  • 分页浏览：按页码、每页条数浏览全部 patch
  • 关键词搜索：按 SHA、标题、作者等搜索
  • 模块筛选：按 21 个标准开发模块筛选
  • 模块统计：展示各模块 patch 数量和评分分布
  • Patch 详情：点击查看单条 patch 的完整 HTML 分析报告

2.8 性能日志（Perf Logs）

自动记录每次分析任务的性能日志，包含：

  • 文件命名：按任务开始时间精确到秒命名
  • 记录内容：各阶段耗时（collecting/analyzing/llm_analyzing）、并发线程数、处理 patch 数量、失败数量
  • 用途：分析性能瓶颈、优化并发参数、评估分析效率

3.2 建议测试项配置（test_suggestions）

测试建议由 test_suggestions 配置块控制，包含两层结构：

  • defaults：所有 patch 默认带上的基础测试建议（5 个维度）
  • rules：按标签（tag）、改动规模（min_churn）等条件命中后追加的建议，多条规则可同时生效

5 个固定输出字段：

配置项类型说明
dimensions数组评分维度定义（id、label、weight）
default_profile对象默认评分配置集（各维度的 score_rules）
blocking_rules数组硬阻断规则列表（命中直接标记为 blocked）
risk_signal_score_rules对象自定义风险信号（检测 CVE、内存操作模式等）
recommendation_mapping数组总分到推荐结论的映射（min/max/recommendation）
test_suggestions对象测试建议配置。包含 defaults（5 个测试维度的默认文案）和 rules（按 tag/churn 等条件匹配的追加规则）
trusted_integration_merge对象集成合并（Merge tag/LTS 合入）的特殊处理：跳过常规降分，总分对齐「建议合入」档位下限
directory_profiles数组按目录前缀匹配的 profile 覆盖（如 mm/ 目录使用不同的权重和测试关注点）
file_profiles数组按文件 glob 匹配的 profile 覆盖（如特定 .c 文件使用不同的权重和测试关注点）
字段说明
unit_test单元测试建议
integration_test集成/API 测试建议
regression_test回归测试建议
manual_validation人工验证建议
release_safeguard发布防护与上线观察建议

rules.match 支持的条件：test_signal、high_risk_paths、min_churn / max_churn、tag（领域标签）、platform（平台标签）。

此外，default_profile.test_focus_hints 以及目录/文件 profile 中的 test_focus_hints 会追加到 manual_validation 字段，用于表达 profile 级别的测试关注点。

6. 后续优化方向

P0 - 模块化重构

patch_analyzer.py（2900行）单体拆分：

  • analyzer/scanner.py：代码扫描（文件解析、diff 分析、metadata 提取）
  • analyzer/scorer.py：评分引擎（维度评分、风险信号评估）
  • analyzer/rules/：YAML 规则加载
  • analyzer/reporters/：输出格式（JSON / HTML / SQLite）

P1 - 多 Tag 区间对比

  • 连续跟踪多个 LTS 版本区间（06→09→12→15_r4）
  • 生成趋势报告：patch 类型分布、风险趋势、模块热度
  • 识别同一上游修复在多个区间重复出现的 Patch

P2 - SQLite 功能拓展

  • 基于 SQLite 的多维度查询（"networking 子系统中风险评分 >7 的 patch"）
  • 按模块、评分、时间筛选和聚合统计
  • 趋势图表可视化

P3 - LLM 分析质量提升

  • 结构化打分脚本与 LLM 评分交叉验证
  • 多模型对比（GPT-4o / Claude / 通义千问等）
  • 分析缓存复用，避免重复 API 消耗

P4 - 自动化 CI 流水线

  • 定时自动拉取新 Tag、分析、生成报告
  • 增量分析（只分析新增 Patch，已有的跳过）
  • 高风险 Patch 告警通知（邮件/IM）

B. 启动方式

# Web 模式
python web_app/app.py
# 打开 http://127.0.0.1:8000

# CLI 模式（区间分析）
python tools/patch_analyzer.py \
  --repo https://android.googlesource.com/kernel/common \
  --from-tag <from_tag> --to-tag <to_tag> \
  --config config/scoring-config.yaml \
  --workers 6 --output outputs/result.json

# CLI 模式（单 SHA 分析）
python tools/patch_analyzer.py \
  --repo https://android.googlesource.com/kernel/common \
  --commit <SHA> \
  --config config/scoring-config.yaml \
  --output outputs/single-result.json

# CLI 模式（使用本地 Git 仓库避免远程 API 限流）
python tools/patch_analyzer.py \
  --repo https://android.googlesource.com/kernel/common \
  --from-tag <from_tag> --to-tag <to_tag> \
  --repo-dir /path/to/local/kernel/repo \
  --config scoring-config.yaml \
  --output outputs/result.json

# 生成 HTML 报告
python tools/render_report.py \
  --input outputs/result.json --output outputs/report.html
