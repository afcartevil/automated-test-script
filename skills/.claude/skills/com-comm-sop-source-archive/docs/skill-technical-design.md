# Android 通信海外售后支持 Skill 技术方案文档

## 1. 文档目的

本文档用于系统说明当前 `android-comm-overseas-support-skill` 的：

1. **生成流程**：从原始培训资料到可落地 Skill 的构建链路
2. **实施方案**：为什么采用当前的分阶段、分层、分批处理方式
3. **Skill 架构**：`SKILL.md` 与 `references/` 的职责划分、知识组织方式与运行规则
4. **扩展路线**：后续如何继续吸收雏鹰资料、案例资料和新培训文档，而不把流程做成“又长又卡”的大链路

本文档面向：

- Skill 建设者
- Android 通信研发/测试支持同事
- 后续接手维护该 Skill 的工程人员

---

## 2. 业务背景与建设目标

### 2.1 业务背景

当前目标是为 **Android 通信研发团队海外印度站点** 建立一套围绕售后问题分析的业务 Skill，帮助海外研发/测试/技术支持团队基于培训资料和 SOP，稳定完成以下动作：

- 问题归类
- 最小证据集收集
- 日志断点定位
- 初步根因判断
- 下一步验证动作
- 升级方向建议

### 2.2 建设目标

Skill 的目标不是“背文档”，而是把零散培训资料沉淀成一套**能被稳定调用的分析知识系统**。它需要满足以下要求：

- **完整性**：至少覆盖 Call、Network、SIM、Stability 四大问题域
- **专业性**：能够引用日志关键字、流程断点、典型判断规则
- **严谨性**：区分“文档支持的结论”和“基于现象的推断”
- **可持续扩展性**：后续能继续吸收雏鹰资料、案例资料和新版本培训文档
- **可控构建性**：构建过程不能依赖超长上下文，也不能每次都全量重跑

## 3. 总体建设思路

### 3.1 两阶段知识策略

整个 Skill 采用 **V1 基线 + V2 补强** 的建设模式：

#### V1：海外对外培训资料基线

优先处理目录：

- `海外研发培训文档/`（培训资料库内相对路径，抽取文本归档于 `source-text/overseas/`）

核心资料为 8 个 PDF，作为对海外可释放的标准分析口径。

V1 的目标是快速形成一套：

- 问题分类框架
- 标准分析流程
- 最小证据集要求
- 通用输出模板
- 升级和分流规则

#### V2：雏鹰培训资料专业补强

在 V1 已成型后，再从 `21/22届雏鹰培训` 中按主题筛选高价值资料，补足：

- 更细的上层/下层流程节点
- 更强的日志断点判断能力
- 更深的网络、SIM、IMS、Modem 领域知识
- 真实案例与复杂场景经验

### 3.2 分层知识设计

当前方案明确采用双层知识结构：

1. **Skill 控制层**：`SKILL.md`
   - 定义角色定位
   - 约束适用范围与不适用范围
   - 约束标准处理流程
   - 约束输出模板和结论表达方式

2. **专题知识层**：`references/*.md`
   - 按问题域拆分知识
   - 保存关键日志、断点、判断规则和升级路径
   - 支撑 Skill 在实际问题中引用知识时的稳定性与可维护性

这比把所有内容塞进一个超长主文件要稳很多。主文件负责“怎么答”，专题文件负责“答什么”。

### 3.3 构建策略

当前已验证有效的构建策略为：

- **单轮只处理一个明确主题**
- **单轮只读取少量必要源文档**
- **抽完立刻落盘，不做跨主题预读**
- **V1 与 V2 不混跑**
- **每轮都必须看到明确的文件产出**

这套策略是从实际卡顿复盘中收敛出来的。说直白点：不再让任务偷偷长胖。

## 4. 原始资料来源与语料边界

### 4.1 已纳入的资料类型

当前允许纳入的文档格式：

- `pdf`
- `pptx`
- `ppt`
- `docx`
- `txt`

### 4.2 明确排除的资料类型

当前阶段明确不纳入：

- `mp4`
- `db`
- 临时锁文件（如 `~$*.pptx`、`~$*.docx`）

### 4.3 资料分层来源

#### A. V1 基线资料

目录：

- `海外研发培训文档/`（培训资料库内相对路径）

用途：

- 构成对外标准培训口径
- 建立 Skill 的首版分析框架
- 统一中英文术语与流程

#### B. V2 补强资料

目录：

- `21届雏鹰培训/`（培训资料库内相对路径）
- `22届雏鹰培训/`（培训资料库内相对路径）

用途：

- 提升 Call / IMS / SIM / Network / Stability 的专业深度
- 补充流程细节、案例经验与日志判断方法
- 作为后续小批次持续增强的候选来源

### 4.4 当前资料目录索引文件

资料索引统一维护在：

- `references/source-inventory.md`

这个文件的作用不是放知识结论，而是维护“有哪些资料值得吸收、优先级是什么、适合补强哪个主题”。

## 5. Skill 生成流程

## 5.1 阶段 1：文档扫描与语料地图建立

先扫描目标目录，完成三件事：

1. 识别可读文件格式
2. 区分海外基线资料与雏鹰补强资料
3. 按主题域建立候选清单

对应产物：

- `references/source-inventory.md`

这一阶段的核心价值是先把资料地图画清楚，避免后面一边做一边乱翻目录。

## 5.2 阶段 2：文档文本抽取

使用本地抽取脚本：

- `tools/extract_training_docs.py`

脚本职责：

- 递归读取输入目录
- 按扩展名分派解析逻辑
- 将 PDF / PPTX / DOCX / TXT 转为可读 Markdown 文本
- 生成 `manifest.json` 记录处理结果

当前技术实现要点：

- `pypdf`：抽取 PDF
- `python-pptx`：抽取 PPTX
- `python-docx`：抽取 DOCX
- 文本文件按多编码顺序尝试读取
- Python 依赖通过工作区本地 `.vendor/python` 使用

当前已完成的抽取结果包括：

- `source-text/overseas/`：海外 8 个 PDF 的抽取文本
- `source-text/v2-plmn/`：单篇 PLMN 课件的 V2 抽取文本

## 5.3 阶段 3：结构化知识提炼

文本抽取只是把文件“变可读”，真正的 Skill 构建在这一步完成。

该阶段会把原始文本提炼成：

- 问题分类框架
- 关键日志关键词
- 断点判断路径
- 场景化分析打法
- 升级建议与材料要求
- 术语表与边界说明

输出位置为：

- `references/*.md`

## 5.4 阶段 4：Skill 控制层封装

在专题知识成型后，再将这些能力统一编排进 `SKILL.md`，包括：

- Skill 定位
- 何时使用 / 何时不要用
- 标准处理流程
- 默认输出模板
- 关键分析原则
- 降级策略与边界声明

这一步把“散的知识文件”封成“能稳定工作的业务 Skill”。

## 5.5 阶段 5：V2 渐进补强

V2 不走全量导入，而走**增量并入**：

1. 锁定一个主题
2. 只抽取 1 份主文档（必要时最多 1 份辅助文档）
3. 提取明确增量
4. 直接写回既有专题文件
5. 同步更新 V2 进度索引

对应索引文件：

- `references/v2-reinforcement.md`

目前已验证这种方式可以稳定推进，不容易再次出现长链路卡顿。

## 6. 当前 Skill 架构设计

## 6.1 目录结构

```text
android-comm-overseas-support-skill/
├─ README.md
├─ SKILL.md
├─ docs/
│  └─ skill-technical-design.md
├─ references/
│  ├─ source-inventory.md
│  ├─ call-analysis.md
│  ├─ network-analysis.md
│  ├─ sim-analysis.md
│  ├─ stability-analysis.md
│  ├─ log-collection.md
│  ├─ escalation-rules.md
│  ├─ terminology-glossary.md
│  └─ v2-reinforcement.md
├─ source-text/
│  ├─ overseas/
│  └─ v2-plmn/
└─ tmp/
```

## 6.2 控制层与知识层职责划分

### `SKILL.md`：控制层

职责：

- 定义 Skill 的角色和用途
- 规定使用范围与边界
- 指定统一处理流程
- 指定默认输出格式
- 约束回答时的证据意识

### `references/*.md`：专题知识层

职责：

- 承载具体分析方法
- 提供各问题域的关键日志、流程断点、归因矩阵
- 分担主文件长度，提升可维护性
- 支持后续逐专题扩展

### `source-text/*`：中间层原料

职责：

- 保存从原始培训文档抽取出来的可读文本
- 作为二次提炼的输入
- 用于复核提炼结论来源

它们不是最终给 Skill 直接引用的稳定知识层，而是构建过程中的“半成品”。

## 6.3 专题知识拆分原则

当前专题拆分遵循“按问题域拆分，而不是按文档来源拆分”的原则。

原因是：

- 实际使用时，用户问的是问题，不是文件名
- 多份文档可能共同支撑同一问题域
- 后续 V2 补强更容易直接并入已有专题，而不是不断新增碎片文件

当前专题如下：

- `call-analysis.md`
- `network-analysis.md`
- `sim-analysis.md`
- `stability-analysis.md`
- `log-collection.md`
- `escalation-rules.md`
- `terminology-glossary.md`

其中：

- 四个主专题负责问题分析
- `log-collection.md` 负责取证规范
- `escalation-rules.md` 负责升级与分流
- `terminology-glossary.md` 负责术语统一

## 6.4 V2 进度控制层

`references/v2-reinforcement.md` 的职责是：

- 记录已完成的 V2 增量
- 记录下一批锁定候选文档
- 规定后续补强顺序
- 提醒执行约束，防止回到“大范围预读”的失控模式

这个文件本质上是 Skill 增量演进的“任务闸门”。没有它，后续补强很容易再次变成到处翻资料、一直不落盘。

## 8. 方案设计 rationale（为什么这样设计）

## 8.1 为什么不把所有内容都放进 `SKILL.md`

因为那样会带来三个问题：

1. 主文件过长，可维护性差
2. 后续补强必须频繁改主文件，风险高
3. 不同问题域之间互相污染，引用成本高

所以当前设计把“流程控制”和“专题知识”拆开，属于典型的**控制层 / 资料层分离**设计。

## 8.2 为什么必须先做 V1 再做 V2

因为 V1 对外资料更稳定、更统一、更贴近海外培训口径。先拿 V1 建基线，能解决两个问题：

- 先把共识口径搭起来
- 避免一开始就被内部资料的深度细节拖进复杂度泥潭

V2 的作用是“补强”，不是“替代基线”。

## 8.3 为什么必须按主题小批次落盘

这是从实际构建事故里换来的经验：

- 跨主题预读会拉长上下文链路
- 提前扫描未来资料会增加无效 IO 和认知噪音
- 没有明确产物的长链路最容易卡在“生成中”

因此当前方案强制要求：

- 一次只做一个主题
- 一次只吸收一个明确增量
- 没落盘就不算完成

## 8.4 为什么保留 `source-text/` 中间层

因为直接从原始文件到最终知识层虽然看起来省事，但实际上不利于：

- 复核提炼依据
- 追踪来源
- 后续重新归纳
- 定位抽取脚本或资料本身的问题

保留中间层，相当于让构建过程具备可追溯性。

## 9. 后续扩展方案

## 9.1 近阶段扩展路线

建议按当前已锁定顺序推进：

1. **Network：APN介绍**
   - 目标：补全 APN 分类、配置来源、数据业务承载差异
2. **SIM：SIM卡识卡流程**
   - 目标：补全检卡时序、上电/复位/ATR、卡槽分层判断
3. **Stability：Modem调试SOP**
   - 目标：补全 dump 抓取、调试入口、协作材料要求
4. **Call / IMS：CS-IMS通话业务介绍**
   - 目标：补全 CS / IMS 域切换、业务流程和典型失败断点

## 9.2 中期扩展路线

在上述补强完成后，可继续扩展到：

- **案例层**：把真实问题案例沉淀成 case-based 参考
- **数据业务层**：补全 Attach、吞吐、AP 侧 data flow 等网络问题
- **平台差异层**：分别强化 MTK / SPRD / Qcom 的差异化判断规则
- **协议深挖层**：对 IMS、UICC、Modem crash 进一步纳入协议与机制材料

## 9.3 结构扩展建议

后续可考虑新增以下专题文件：

- `references/case-studies.md`
- `references/platform-differences.md`
- `references/data-service-analysis.md`
- `references/ims-deep-dive.md`

但新增文件要满足一个前提：

> 只有当某类知识已经明显超过现有专题的合理边界时，再新开文件；不要为“看起来整齐”而无意义拆分。

## 9.4 运行能力扩展建议

除了文档本体，后续还可考虑建设：

1. **案例验证集**
   - 用典型售后问题验证 Skill 是否能正确归类、抓取证据、给出断点和升级建议

2. **引用校验机制**
   - 对 Skill 输出增加“引用了哪个专题文件/哪类依据”的校验习惯

3. **版本化发布**
   - 例如：`V1.0 基线版`、`V1.1 网络补强版`、`V1.2 SIM/Modem 补强版`

4. **增量构建记录**
   - 每次补强记录来源文档、吸收内容、落盘位置与未解决边界

## 10. 风险、约束与控制措施

| 风险 / 约束 | 说明 | 当前控制措施 |
| --- | --- | --- |
| 资料量过大 | 一次全量处理容易卡顿、遗漏或失控 | 改为单主题小批次落盘 |
| 资料来源口径不一致 | 不同讲师术语、结论可能不一致 | 统一沉淀进术语表与专题规则 |
| 对外资料深度不足 | V1 可用但不够深 | 用 V2 做渐进补强 |
| 复杂案例无法直接下结论 | 资料边界不足时容易误判 | `SKILL.md` 强制输出边界声明与降级策略 |
| 原始文件格式多样 | 抽取质量存在差异 | 保留 `source-text/` 中间层便于复核 |
| 构建链路过长 | 容易出现长时间“生成中” | 禁止跨主题预读与混合链路 |

---

## 11. 推荐维护流程

后续维护建议遵循以下固定步骤：

1. 在 `v2-reinforcement.md` 里锁定下一批唯一主题
2. 只抽取该主题的 1 份主文档
3. 在 `source-text/` 下保留抽取文本
4. 将增量写回对应 `references/*.md`
5. 更新 `v2-reinforcement.md` 的“已吸收增量”和“下一批候选”
6. 若涉及结构变化，再更新本技术文档

这样能保证 Skill 长期演进时，结构不散、节奏不乱、知识可追溯。

## 12. 当前结论

当前 `android-comm-overseas-support-skill` 已经不是一个“待搭建的想法”，而是一套已经完成 V1 主体、并进入 V2 渐进补强阶段的业务 Skill。

其核心技术方案可以概括为：

- **资料分层**：V1 基线 + V2 补强
- **知识分层**：`SKILL.md` 控制层 + `references/` 专题知识层 + `source-text/` 中间层
- **执行策略**：单主题、小批次、直接落盘
- **演进策略**：通过 `v2-reinforcement.md` 做增量闸门与路线管理

这套方案最大的价值不是“文档很多”，而是：

> 它已经把一堆培训材料，变成了一套可持续构建、可追溯维护、可逐步增强的通信售后分析知识系统。
