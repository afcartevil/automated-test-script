# Hang 详细分析步骤

## 总流程

1. 场景分型（先判断卡在哪里）
2. 线程状态定位（找关键阻塞线程）
3. 阻塞因果链构建（blocked -> resource -> owner）
4. 等待点分支判断（锁/内存/I-O/Binder）
5. 输出结论与 Jira 行动项

## 步骤1: 场景分型

### 目标
快速确定卡死发生阶段，缩小分析范围。

### 操作
1. 查看 `_分析报告.txt` 与 `SYS_HANG_DETECT_RAW` 的描述。
2. 区分以下分型:
   - 关机/重启阶段 hang
   - system_server/watchdog 无响应
   - 运行期资源枯竭或高负载阻塞
3. 记录异常前关键操作与时间点。

## 步骤2: 线程状态定位（Thread info）

### 目标
确定“谁被卡住、卡在什么资源上”。

### 操作
1. 在 `SYS_HANG_DETECT_RAW` 中检索 `watchdog`、`D` 状态、关键线程名。
2. 记录线程状态: `Running/Runnable/D/Uninterruptible`。
3. 对每个关键线程记录:
   - 线程名 / tid / cpu
   - 当前等待点函数
   - 等待对象（锁、页、I-O、服务）

## 步骤3: 构建阻塞因果链

### 目标
从现象栈到根因链路，不做单点结论。

### 操作
1. 从被阻塞线程回溯到等待资源。
2. 继续查找资源 owner（持锁线程/被调服务/下层设备）。
3. 建立链路:
   - `blocked thread -> wait object -> owner -> owner 状态`
4. 若只找到 wait 点，标记“owner 未确认”，作为待验证项。

## 步骤4: 分支分析

### A. 锁等待类

关键词/函数:
- `__mutex_lock`
- `ww_mutex_lock`
- `rwsem_down_*`
- `futex`

判断方向:
- 死锁
- 锁顺序反转
- 长临界区

输出要点:
- 锁类型、等待线程、owner 线程、持锁时长证据

### B. 内存/缺页等待类

关键词/函数:
- `do_translation_fault`
- `folio_wait_bit_common`
- `kswapd`
- `ion`
- `slab`

判断方向:
- 内存压力导致长期不可运行
- 内存泄漏（ion/slab 持续增长）
- 直接回收/频繁回收引发卡顿

输出要点:
- 内存关键指标与时间点
- 与阻塞线程的关联性

### C. 文件系统/I-O 等待类

关键词:
- `blockio`
- `timeout`
- `bio`
- `blk`
- `fs wait`

判断方向:
- 存储设备超时或重试
- 下层设备导致上层服务阻塞

输出要点:
- I-O 错误/超时日志
- 设备路径与受影响线程

### D. 服务链路阻塞类

关键词:
- `binder`
- `system_server`
- `watchdog`

判断方向:
- 单点服务拥塞放大为系统级 hang
- 主线程/关键线程被同步调用阻塞

输出要点:
- 调用方线程
- 被调服务线程
- 阻塞链路闭环

## 步骤5: Jira 结论输出

最少输出:
1. 触发场景
2. 关键阻塞线程
3. 等待点函数
4. owner/根因方向

证据三件套:
- 线程栈链路
- 内核关键日志
- 时间线（前因后果）

结论要求:
- 标注置信度（高/中/低）
- 区分已证实/待验证
- 给出下一步动作（补日志/复现/模块 owner）
