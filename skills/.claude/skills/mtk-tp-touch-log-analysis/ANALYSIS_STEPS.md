# 详细分析步骤

## 分析流程概览

按 SOP 固定顺序执行：

1. 获取日志
2. 判断问题
3. 分析日志

只有先确认问题场景和对应时间段，后续的 `kernel_log` 判断才有意义。

## 步骤1：获取日志

### 目标

确认当前输入中已包含可用于 TP 触摸失效分析的有效日志。

### 操作

1. 从 JIRA 的 `Log and Screenshot address` 获取 `mobilelog`，或者使用用户提供的 log 地址。
2. 获取 `mobilelog` 后，提取 APLog 中的 `kernel_log`。
3. 同时提取 `boot_normal` 中的 `kernel_log`，作为开机阶段 TP 初始化分析入口。

### 判断条件

| 条件 | 结论 | 下一步 |
|---|---|---|
| 未获取到 `kernel_log` | 无法继续分析 | 停止分析并说明缺失项 |
| 已获取到 `kernel_log` | 满足分析前提 | 进入步骤2 |

## 步骤2：判断问题

### 目标

根据问题现象选定需要重点查看的日志时间段。

### 操作

1. 如果是开机无触摸，优先查看 `boot_normal` 中的 `kernel_log`。
2. 如果是亮灭屏无触摸，查看相应时间点的 `kernel_log`。

### 判断条件

| 条件 | 结论 | 下一步 |
|---|---|---|
| 开机无触摸 | 重点看开机阶段 TP 初始化和驱动加载 | 进入步骤3 |
| 亮灭屏无触摸 | 重点看对应时间点 TP 状态和报错 | 进入步骤3 |

## 步骤3：分析日志

### 目标

确认 TP 驱动是否初始化成功，若失败则定位 fail 报错；若成功则继续确认是否已有触摸数据上报。

### 操作

1. 首先搜索是否有初始化成功的关键字，重点查看：
   - `flod_main_device_init`
   - `tpd_probe`
   - `match_tp_controller`
2. 如果没有初始化成功的打印，则查看具体的 fail 报错。
3. 如果有初始化成功的打印，则查看是否有触摸数据上报，重点查看：
   - `fts_input_report_b`
   - `touch down`
   - `touch up`
4. 如果已有触摸数据上报，则将结论转交上层同事继续排查分析。
5. 根据报错日志，给出排查方向；如果证据充分，也可以直接给出根因，并补充修改代码方向作为参考。

### 判断条件

| 条件 | 结论 | 下一步 |
|---|---|---|
| 存在初始化成功关键字，且有 `touch down/up` 上报 | TP 驱动已基本正常工作 | 转上层继续分析 |
| 存在初始化成功关键字，但无触摸数据上报 | 继续结合运行期异常收敛 TP 侧问题 | 输出 TP 运行链路异常结论 |
| 不存在初始化成功关键字，且有明确 fail 报错 | 优先收敛为 TP 驱动 / 硬件 / 供电 / 复位链路异常 | 输出 TP 初始化失败结论 |

## 常用检查顺序

1. 先看 `bootmode` 是否允许加载。
2. 再看 `tpd_probe` 是否启动。
3. 再看 `match_tp_controller` 是否匹配到正确 `vendor` / `ic` 并初始化成功。
4. 最后看 `fts_input_report_b` 是否存在触摸 down/up 上报。
