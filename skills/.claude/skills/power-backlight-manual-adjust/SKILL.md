# 手动背光调节异常分析

## 适用范围

本场景用于指导以下“手动亮度链路”的首轮分析与归因：

- 拖动亮度条后 **亮度不跟随变化**（UI 有变化但屏幕亮度不变）
- 拖动过程中 **亮度变化卡顿/不连续**（跳变、停住、闪烁）
- 拖动结束后 **亮度回跳**（回到拖动前或某个固定值）
- 拖动结束后 **无法保持**（几秒后被自动亮度/策略覆盖）
- 系统侧目标亮度与 **HAL/驱动实际写入值不一致**

---

## 不适用场景（避免误用）

以下现象不建议直接用本场景下结论，需先路由到更合适专题：

- **自动亮度问题**（未手动拖动，环境变化导致亮度异常）：优先 `power-backlight-auto-anomaly`
- **相机/视频专属策略**（仅在相机/视频播放时异常）：优先 `power-backlight-camera-video`
- **遮挡/口袋/接近传感器导致的亮度/亮屏变化**：优先 `power-sensor-proximity-brightness`
- **HBM 进入/退出异常**：优先 `power-backlight-hbm-enter`

如果用户明确“没有拖动亮度条”，不要按手动链路分析。


## 公共亮度策略前置检查
在判定当前场景为异常前，必须先排查以下正常亮度策略是否正在生效：温控限亮、App 降亮度、常温最大亮度限制、户外增强、省电模式。
判断优先级：温控优先级最高；没有温控时，如果多个亮度策略同时存在，通常谁计算出的亮度最低就使用谁的亮度。户外增强属于增亮策略，但可能被温控、省电或最大亮度限制压住。
如果日志命中 `power-backlight-policy-factors` 中的策略证据，应在结论中单独说明：命中的策略、关键日志、该策略导致亮度上升/下降/限制上限，以及这是正常策略生效还是“该触发未触发 / 不该触发却触发”的策略异常。

## 分析前的最小证据集

开始分析前，优先补齐这些信息（信息不全时先补齐，不要直接归因）：

- 发生入口：状态栏亮度条 / 设置页亮度条 / 快捷面板
- 发生时间点（分钟级）与持续时间（拖动时/拖动后多久回跳）
- 自动亮度开关状态（开/关）
- 是否处于特殊场景：通话遮挡、相机、视频、强光、低电量、省电模式
- 是否可稳定复现、是否与对比机一致（DUT/REF）
- 机型/版本/平台（MTK/QCOM/UNISOC）

### 3.1 推荐优先查看的日志

- `mainlogcat-log*` / `main_log*`：Framework 侧 DisplayPowerController/PowerManagerService 关键日志
- `sys_log*` / `systemlogcat-log*`：系统服务侧亮度/电源策略、HAL 调用相关日志
- `0-android_main.log*` / `0-android_system.log*`：部分版本关键线索落在此处

---

## 快速判断（是否命中手动亮度链路）

命中以下信号通常可确认属于手动亮度链路（不要求全命中，但至少应出现“拖动触发/目标变化”的证据）：

- 拖动触发路径（常见 reason 切到 temporary）：
  - `DisplayPowerController2[0].*temporary`
- 目标亮度变化记录（动画/目标收敛）：
  - `DisplayPowerController2[0].*animateScreenBrightness`
- 背光写入证据（不同平台路径不同，本文 match_patterns 已覆盖常见路径）：
  - `android.hardware.lights-service.mediatek.*/sys/class/leds/lcd-backlight/brightness`
  - `LIGHTS.*/sys/class/backlight/sprd_backlight/brightness`

如果完全找不到上述信号，优先考虑：日志不全/时间窗口不对/场景未命中，先补齐证据。

## 正常链路参考（用于和当前日志对比）

正常手动亮度链路应当能看到下面的阶段顺序。飞书里的正常打印案例只用于对比链路完整性，不作为当前问题证据。

1. 用户拖动亮度条，系统进入临时亮度或手动调节路径，常见表现为 reason 临时切换到 `temporary`。
2. Framework 接收到新的目标亮度，`animateScreenBrightness` 或同类日志体现目标值随拖动变化。
3. 拖动过程中目标亮度应连续变化，变化方向应与用户拖动方向一致。
4. 拖动结束后，临时状态应恢复到可持久的 manual 状态，避免被策略回滚。
5. HAL / backlight 写入值应跟随 Framework 目标变化。
6. 如果自动亮度开启，拖动后的保持行为还要结合自动亮度策略判断，不能简单认定为回跳异常。

如果当前日志只看到 UI 行为但看不到 Framework 目标变化，应优先怀疑时间窗口、日志缺失或输入链路未进入系统服务。

### 与飞书正常案例的对比方式

- 对比拖动开始、目标变化、拖动结束恢复、背光写入四个阶段是否齐全。
- 正常案例中的打印只能说明“正常链路通常包含这些阶段”。
- 当前问题的结论必须引用当前日志中的 `temporary`、`animateScreenBrightness` 或背光写入证据。

## 标准处理流程

> 要求：先找“流程断点”，再谈根因。每一步都给出 **目标**、**证据**、**判断分支** 与 **下一步动作**。

### Step 1：检查拖动是否触发临时亮度路径（`check_temporary_reason`）

- **目标**：确认拖动行为已进入手动拖动链路（temporary）。
- **关键证据**：`DisplayPowerController2[0].*temporary`
- **判断分支**：
  - **若存在**：进入 Step 2
  - **若不存在**：
    - 可能原因：时间窗口不对 / 日志缺失 / 实际不是手动拖动
    - **下一步动作**：让用户提供更准确时间点；补齐 `mainlogcat-log*`；确认是否真的拖动亮度条

### Step 2：检查目标亮度是否随拖动变化（`check_brightness_animation`）

- **目标**：确认系统侧目标亮度确实在变化（排除“UI 动了但系统目标没变”）。
- **关键证据**：`DisplayPowerController2[0].*animateScreenBrightness`
- **判断分支**：
  - **存在连续变化**：说明系统侧接收到了拖动意图 → 进入 Step 3
  - **不连续/缺失**：可能是输入事件未到系统服务、策略被打断或动画被抑制
    - **下一步动作**：结合 Step 4 的写入证据判断是“系统目标没变”还是“写入没跟上”

### Step 3：检查拖动结束后是否恢复到可持久状态（`check_manual_restore`）

- **目标**：拖动结束后 reason 是否从 temporary 恢复到 manual（或进入持久化路径），否则容易出现“回跳/不保持”。
- **关键证据**：`DisplayPowerController2[0].*temporary`（结合前后时序判断是否恢复）
- **判断分支**：
  - **能恢复**：进入 Step 4
  - **不能恢复**：高概率导致拖动结束后被策略覆盖或状态机卡住
    - **下一步动作**：检查是否开启自动亮度/省电/特殊场景（通话遮挡、相机、视频）导致策略覆盖

### Step 4：检查 HAL/驱动背光写入是否与目标一致（`check_backlight_write`）

- **目标**：把问题落到“系统目标”还是“实际写入”。这是该场景最关键的分界线。
- **关键证据**：背光节点写入相关日志（本文 match_patterns 覆盖的路径正则）
- **判断分支**：
  - **目标变化但写入不变/落后**：偏向 HAL/驱动写入链路异常、节点权限/映射问题
  - **目标本身就没变化**：偏向 Framework 策略/状态机/输入链路问题
  - **写入与目标一致但用户仍感知异常**：考虑亮度曲线/校准/面板特性/视觉感知（需要更进一步数据）

### Step 5：输出结论（建议结构）

- **问题类型**（建议枚举）：
  - 系统侧目标未更新
  - 目标更新但动画/收敛被打断
  - temporary 未恢复导致不保持/回跳
  - HAL/驱动写入异常（写入不一致、路径不对、写入失败）
- **关键证据**：按时间顺序列出 3~5 条关键日志（包含对应模式）
- **下一步动作**：给出 1~3 个最小验证动作（补日志/复现时记录时间点/切换自动亮度开关对比等）
- **修复建议**：Framework 策略/状态机修复、HAL 写入链路排查、节点权限与映射检查

## 常见根因地图（示例）

| 根因方向 | 典型证据 | 建议动作 |
|---|---|---|
| 输入/策略未进入手动链路 | Step 1 不出现 temporary | 补齐时间窗口与 main log；确认是否真的拖动亮度条 |
| 系统目标不随拖动变化 | Step 2 animateScreenBrightness 缺失/不连续 | 排查输入链路与策略覆盖；对比自动亮度开关 |
| temporary 不恢复导致回跳 | Step 3 无恢复迹象 | 检查自动亮度/省电/遮挡/相机视频等覆盖策略 |
| HAL/驱动写入不跟随 | Step 2 目标变化，但 Step 4 写入证据不一致 | 排查 lights HAL、背光节点路径、权限与映射 |

---

## 常用回答动作（信息不足/不确定时）

- **缺少时间点**：先让用户提供“开始拖动”和“异常发生/回跳”的时间点
- **不确定是手动还是自动**：让用户确认是否拖动亮度条；并补充自动亮度开关状态
- **缺少写入证据**：提示补齐系统 log/主 log，并扩大关键词（backlight/brightness/lights）
- **跨场景干扰**：提示用户说明是否在通话遮挡/相机/视频/省电模式下复现

---

## 失败时的降级策略

当无法得出可靠根因时，按以下方式降级：

1. 明确当前只能定位到哪一层（Framework 目标 vs HAL 写入）
2. 列出缺失证据（哪类日志/哪个时间窗口）
3. 给出最小验证动作（优先 1 个）
4. 如需接力：说明承接方向（Framework/HAL/驱动）与交接材料

---

## 证据约束

- 没有拖动触发/temporary 证据时，不能确认进入手动亮度链路。
- 没有目标亮度变化证据时，不能判断 HAL/驱动异常。
- 没有背光写入证据时，只能定位到 Framework 目标层或状态机层。
- 如果自动亮度开启，拖动后的回落不一定是异常，必须结合策略覆盖证据。
- Markdown 和飞书正常案例只用于指导对比，不是当前问题事实。
