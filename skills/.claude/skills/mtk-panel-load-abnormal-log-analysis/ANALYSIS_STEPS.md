# 详细分析步骤

## 步骤1：日志完整性校验

### 操作细则

1. 确认已获取的日志文件：
   - 串口Log：用于分析LK阶段运行情况
   - Kernel Log：用于分析Kernel阶段运行情况
   - Mobile Log：若存在mobilelog文件夹，提取`kernel_log`和`main_log`

2. 过滤并排除与显示领域无关的日志文件：
   - 排除modem_log、radio_log等非显示相关日志
   - 仅保留SOP定义的有效日志文件

3. 若存在mobilelog文件夹：
   - 提取`APLog_*/kernel_log_*`作为kernel_log
   - 提取`APLog_*/main_log_*`作为main_log
   - 开机阶段日志优先提取`boot_normal`子文件夹内的文件

### 判断标准

- **无串口Log且无Kernel Log**：停止分析，提示用户需提供至少一份日志
- **有串口Log无Kernel Log**：可分析LK阶段，但Kernel阶段分析受限
- **无串口Log有Kernel Log**：跳过LK阶段，直接进入Kernel阶段分析
- **两者齐全**：按LK→Kernel顺序完整分析

## 步骤2：日志关键字过滤

### 操作细则

1. 在串口Log（LK阶段）中搜索以下关键字（不区分大小写）：
   ```
   lcm|panel|disp|dsi
   ```

2. 在Kernel Log中搜索以下关键字（不区分大小写）：
   ```
   lcm|panel|drm|hwc|surfaceflinger|disp|dsi
   ```

3. 分别整理LK阶段和Kernel阶段的过滤结果，按时间排序

### 判断标准

- **过滤结果完全为空**：扩大关键字范围，或确认日志文件是否正确
- **过滤结果非空**：提取关键行，进入步骤3

## 步骤3：问题阶段判定

1. 若存在LK阶段串口日志，**优先分析LK阶段是否存在异常**
2. 若不存在LK阶段串口日志，直接进入Kernel阶段分析
3. 判定问题可能发生的阶段后，进入步骤4

## 步骤4：分阶段日志分析

### 4.1 LK阶段分析（按优先级排序）

#### 检查1：屏幕识别流程入口
- **搜索关键字**：`we will check lcm`
- **搜索目标**：确认LK是否执行了屏幕识别流程
- **判断**：
  - 未打印 → LK阶段未执行屏幕识别流程，可能是Boot流程在更早阶段出现问题
  - 已打印 → 记录屏幕名称和检查序号，继续检查2

#### 检查2：屏幕识别结果
- **搜索关键字**：`islcmfound`
- **搜索目标**：确认`islcmfound`字段值
- **判断**：
  - `islcmfound = 0` → LK阶段屏幕加载失败，未识别到有效屏幕（主结论）
  - `islcmfound = 1` → LK阶段屏幕识别成功，继续检查3

#### 检查3：屏幕型号匹配
- **搜索关键字**：`lcm_name`
- **搜索目标**：确认识别的屏幕名称是否与硬件匹配
- **判断**：
  - `lcm_name = [屏幕名]` → 确认屏幕型号是否与预期一致

#### 检查4：EPC寄存器读取
- **搜索关键字**：`lcm_epc_read`
- **搜索目标**：确认`epc_strings`的值
- **判断**：
  - 数值全为0（如`000000000000000000000000000000000000`） → 屏幕寄存器读取失败，屏幕硬件未连接或上电异常
  - 数值非全0 → 屏幕寄存器读取正常

#### 检查5：Panel上电初始化
- **搜索关键字**：`lcm_get_params.*lcm power init`
- **搜索目标**：确认Panel上电初始化流程是否执行
- **判断**：
  - 同项目正常日志有该打印、异常日志无打印 → Panel上电流程未正常执行

#### 检查6：LK初始化完成确认
- **搜索关键字**：`lcm_init is cmd|mt_disp_init`
- **搜索目标**：确认LK阶段初始化是否完成
- **判断**：
  - 有`lcm_init is cmd = 0 --`且`mt_disp_init`打印 → LK初始化正常完成
  - 无上述日志 → LK初始化未完成

### 4.2 Kernel阶段分析（按优先级排序）

#### 检查1：DRM模块加载
- **搜索关键字**：`Loading module.*mediatek_drm`
- **搜索目标**：确认MTK DRM模块是否被加载
- **判断**：
  - 无该日志 → DRM驱动模块未加载（主结论）
  - 有该日志 → 检查后续是否有`mtk_drm`相关流程日志，确认模块加载正常

#### 检查2：Panel Probe流程
- **搜索关键字**：`lcm_probe begin|lcm_probe end`
- **搜索目标**：确认begin和end是否成对出现
- **判断**：
  - begin和end成对出现 → Panel probe正常完成
  - 仅有begin无end → Panel probe流程执行失败，导致Panel加载异常（主结论）

#### 检查3：DSI驱动等待
- **搜索关键字**：`Waiting for bridge or panel driver`
- **搜索目标**：确认DSI等待日志的出现频率和分布
- **判断**：
  - 仅DRM加载前期少量打印 → 属于正常现象，DSI正在等待Panel驱动就绪
  - DRM加载完成后持续打印、或日志全程持续打印 → Panel加载失败（主结论）

#### 检查4：GPIO引脚配置
- **搜索关键字**：`Cannot find disp pinctrl`
- **搜索目标**：确认是否存在GPIO配置错误
- **判断**：
  - 打印该日志 → 屏幕引脚配置错误，需排查`.dts`和`.dws`文件中的GPIO配置（主结论）

#### 检查5：扩展检查
若上述4项检查均无异常，可扩展检查：
- GPU加载日志：搜索`mali|gpu|GPU`
- SurfaceFlinger启动日志：搜索`SurfaceFlinger`
- HWC异常日志：搜索`HWC|hwcomposer`

## 步骤5：根因定位与输出

1. 汇总步骤4中所有异常发现
2. 按可能性从高到低排序根因候选（优先排序有明确日志证据的根因）
3. 每条根因必须附带对应的原始日志行
4. 给出最小可验证的排查步骤
5. 仅在有明确日志证据时给出补丁方向
