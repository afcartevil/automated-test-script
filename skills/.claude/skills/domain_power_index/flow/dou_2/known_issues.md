# DOU 已知问题库

**用途**：单场景综合 AI / TopN 总结前必须先对照本文件。  
**命中时**：结论中明确标注「已知问题」，按本条「判定要点 / 处理建议」书写，**不要**把该现象当作新的版本功耗回归根因反复深挖。  
**未命中**：按正常分析流程继续。  
**门禁**：每条目的「特征 / 判定要点」中的**量化门槛**（如 CPU 占用率）须**同时满足**才算命中；仅进程名或现象相似但**未达门槛** → **不得**判定为该已知问题。

新增条目时请追加在文末，保持 `KI-xxx` 编号递增。

## KI-001：`ocessService0:0` / SandboxedProcessService 持续高 CPU（沙箱进程）

| 项 | 说明 |
|----|------|
| **特征** | 进程名形如 `ocessService0:0`、`SandboxedProcessService0:0`、`*:sandboxed_process*` 等；且 CPU **持续占用率 ≥ 约 70%**（高功耗侧 Top 进程占比或时段内 CPU 使用率） |
| **本质** | **沙箱进程**，不是业务主进程本身 |
| **判定要点** | 0）**CPU 占用率未达约 70% → 不命中本条**，按正常流程分析；1）不要把 `ocessService0:0` 单独定性为根因；2）在同场景 Top 进程列表中查找**与它一起出现、同属同一应用/同时间段**的进程，那才是**主进程**；3）主进程通常为完整包名或带业务后缀的进程（如宿主 App、WebView 宿主等） |
| **处理建议** | 结论中写明「沙箱高 CPU，属已知问题形态」；根因与验证动作应锚定**主进程 + 沙箱伴随关系**（包名、业务场景、是否 WebView/Chrome 类沙箱），而非只报 `ocessService0:0` |
| **关键词** | `ocessService0:0`、`SandboxedProcessService`、`sandboxed_process`、沙箱、sandbox |

## KI-002：`messenger.sms` 反复崩溃又重启（PID 不断更换）

| 项 | 说明 |
|----|------|
| **特征** | 进程 `messenger.sms`（或相关 Messenger SMS 组件）**反复崩溃后重启**，日志/CPU 中可见 **PID 不断更换** |
| **本质** | 预加载相关问题；视频划动场景下可能存在**误触**触发；已在 **CN6 主干**优化合入，将该预加载加入黑名单 |
| **判定要点** | 1）出现 `messenger.sms` 崩溃重启 + PID 变化时，优先对照本条，不当作新功耗回归；2）结合场景视频，观察划动是否误触；3）确认分析版本是否已包含下方合入 |
| **处理建议** | 结论标注「已知问题」；建议核对版本是否已合入预加载黑名单修复；未合入版本可指向合入链接跟进，目前已知合入CN6 |
| **合入链接** | https://gerrit.transsion.com/c/TRAN_CODE/THUB/thub_core_factory_opt_performance_services/+/1552743 |
| **关键词** | `messenger.sms`、崩溃、重启、PID、预加载、黑名单、误触、视频划动 |
