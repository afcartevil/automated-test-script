## 3. 总流程（每个 TopN suffix）

```
前置门禁
  → 步骤 A：读 YAML，逐步写出操作与用时
  → 步骤 B：按行为路由到场景分析章节
  → 步骤 C：操作区间对齐电流 / spike / CPU
  → 步骤 D：按场景章节做 P0 深挖
  → 步骤 E：对照已知问题库（KI）
  → 步骤 F：填写标准结论
  → 下一 TopN
全部完成后：若有商店下载类 → 确认 app_download 已跑 → 回到 dou_2 总结/HTML
```

### 3.1 步骤 A — 读取 YAML 操作时间轴

**数据位置**：`<高功耗目录>/meta_report/*_{pass|error}_dou3_<suffix>.yaml`  
**关键字段**：`case_desc`；`data.step_time_datas[]` 的 `step_name` / `sub_step_name` / `expect_time` / `actual_time`

**读取命令**：

```powershell
python analysis/domain/power/flow/dou_2/scenario/scripts/read_scene_yaml_ops.py `
  "<高功耗目录>\meta_report" "<suffix>"
```

脚本输出含相对场景起点的 `t0_sec` / `t1_sec`（与 pt5、`diff_segments` 同轴）、`op_kind`、`is_setup`。

**写出要求（强制）**

- **每个操作一行**：`step_name`、`sub_step`（若有）、`[t0, t1)`、**用时=`actual_time`**、`op_kind`
- 禁止只写「本场景共 xxx 秒」
- `case_desc` 与操作不一致时，把告警原文写入结论，后续以 YAML 为准

**Setup 降权（可写进时间轴，不当主因）**

`确保退到桌面`、`识别黑屏解锁`、`左右滑桌面`、`搜索打开*`、`退到桌面`/`退回桌面`/`回到桌面`、`单用例结束机械手回轴`



### 3.3 步骤 C — 操作区间对齐电流

**输入**：步骤 A 的逐步时间轴 + `current_cpu_spike_<suffix>.json`

对每个**业务**操作 `[t0, t1)`：

1. 重叠的 `diff_segments`（`mean_diff_ma`、`delta_from_prev_ma`）
2. 落入区间的 `spike_windows`
3. 对应 `cpu_in_segment` Top 进程
4. 对照下表判定「符合操作预期」或「异常」

| op_kind | 预期电流形态 | 异常（需深挖） |
|---------|--------------|----------------|
| `app_idle` | 平坦中高平台，尖峰稀疏 | 平台过高；或密周期尖峰 |
| `feed_scroll` / `video_or_feed_scroll` | 中高平台 + 周期尖峰（**详见 §4**） | 停滑不掉电；尖峰过密；沙箱空转 |
| `video_watch` / `video_pip` | 高平台、相对平滑 | 小窗段仍密尖峰；解码不释放 |
| `media_filter_edit` | 每次操作脉冲簇 + 中高平台 | 无操作时平台仍很高 |
| `camera_shot` | 快门/后处理尖峰簇 | 无尖峰结构的持续高平台 |
| `content_record` / `content_publish` / `content_upload` | 录制抬升 → 上传台阶 | 结束后平台不回落 |
| `store_download` | 下载段持续中高 | 无 DOWNLOADING 却抬升 |
| `maps_nav` | 高平台持续 | 与定位无关的密尖峰 |
| `document_browse` | 中平台 + 翻页尖峰（**滑动步走 §4**） | 整段被同步抬高 |
| `web_browse` | 打开尖峰 + 滚动尖峰（**滚动步走 §4**） | 只报沙箱不报宿主 |
| `media_edit` | 高平台（GPU/多路 decode） | 预览/导出未拆分 |
| `setup` / `app_launch` | 短尖峰 | **禁止当主因** |

**多段场景必须拆开写**：滑动 vs 小窗；浏览 vs 下载；录制 vs Share。  
**公平性**：high/low 同一步 `actual_time` 差很大 → 先标脚本差异，再谈版本回归。

### 3.4 步骤 D — 场景深挖

按步骤 B 进入第 6 章对应小节；YAML 含滑动步时**先执行 §4**，再叠加场景专属步骤。

### 3.5 步骤 E — 已知问题（KI）

对照 `../known_issues.md`：

| 编号 | 摘要 | 处理 |
|------|------|------|
| KI-001 | 沙箱进程（`ocessService` / `SandboxedProcess`）持续高 CPU（**≥ 约 70%**） | CPU 未达门槛 → **不命中**；命中则标已知问题，根因锚定**宿主进程 + 沙箱伴随**，勿只报沙箱名 |
| KI-002 | `messenger.sms` 反复崩溃重启（PID 更换），划动误触/预加载 | 标已知问题；核对是否已合入黑名单修复，勿当新回归反复深挖 |

未命中 → 写「非已知问题库条目」。

### 3.6 步骤 F — 标准结论模板

```text
【SOP-DOU-SCENARIO-01】

- suffix / 场景名(desc):
- YAML 操作与用时（逐步，禁止只写总时长）:
  - <step_name> [<t0>, <t1>) 用时=<actual_time>s op_kind=
  - …
- desc与操作校正: <无 / 告警原文>
- 功耗差异 Δ: <与 TopN 一致>
- 电流形态: <平台 | 周期尖峰 | 脉冲簇 | 泄漏>；是否符合该步预期: <是/否>
- 主因进程: <包名/进程；有沙箱写清宿主关系>
- 证据:
  - 电流: …
  - CPU/log: …
- KI: <KI-xxx | 非已知问题库条目>
- 建议验证:
```

**合格标准**：字段齐全；YAML 逐步用时已写；≥1 个业务时间窗 + ≥1 个电流证据 + ≥1 个进程/log 证据。

## 4. 滑动场景（共性分析方法）

> **定位**：Feed 滑动、视频信息流滑动、文档翻页、商店列表滑动、网页滚动等，电流形态与排查路径高度相似。  
> **用法**：YAML 业务步命中滑动类 `op_kind` 或步名含滑动关键字时，**先按本节完成滑动步分析**；场景章节只写该场景专属补充（小窗/下载/同步等）。

### 4.1 何谓「滑动步」

| 识别方式 | 示例 |
|----------|------|
| `op_kind` | `feed_scroll`、`video_or_feed_scroll`；或 `document_browse` 中的滑动步 |
| YAML `step_name` / `sub_step_name` | `滑动浏览`、`主界面观看`、`短距离滑动`、`循环滑动`、`上下滑动`、`滑动查看文档` |
| 典型 `sub_step` | `每3秒循环滑动`、`循环短距离滑动`、`滑动浏览` |

**不属于滑动步（勿套用本节）**：小窗长播（`video_pip`）、下载（`store_download`）、录制/上传、滤镜脉冲、纯待机、导航持续高平台。

### 4.2 共性：预期电流形态

| 形态 | 说明 | 异常 |
|------|------|------|
| **中高平台** | 滑动期间底电抬高 | 平台明显高于低功耗版且无对应 CPU |
| **周期尖峰** | 与 `sub_step` 滑动节奏对齐（如每 3s 一次） | 尖峰过密/无节奏/停滑仍密 |
| **停滑回落** | 两次滑动之间电流应有所回落 | 停滑后平台不掉 → 预取/泄漏/空转 |
| **文档翻页变体** | 中平台 + 翻页尖峰（幅度通常小于 Feed 密尖峰） | 整段被后台同步持续抬高 |

### 4.3 共性：分析侧重点

| 优先级 | 查什么 | 说明 |
|--------|--------|------|
| P0 | **尖峰周期 ↔ sub_step** | 如「每3秒循环滑动」应对齐 spike 间隔 |
| P0 | **宿主 vs 沙箱**（KI-001） | `ocessService`/`sandboxed_process` 高 CPU 时锚定宿主包 |
| P0 | **渲染/解码负载** | 图片解码、列表合成、WebView 渲染 CPU |
| P1 | **预取 / 广告 SDK** | 仅 high 侧多出的伴随进程 |
| P1 | **停滑掉电** | 滑动段 vs 段内停顿/段间平台差 |
| P2 | **划动误触**（KI-002） | `messenger.sms` 崩溃重启；视频/Feed 划动类多见 |

### 4.4 共性：Log / 数据锚点

- **CPU**：宿主包名 + `sandboxed_process` / `ocessService` / `gpu-process`（浏览器）
- **电流**：`diff_segments` 重叠滑动窗；`spike_windows` 周期
- **main**：`Choreographer`、`HWUI`、`ImageDecoder`、`Glide`/`Coil`、`WebView`/`Chromium Render`
- **公平性**：high/low 同一步 `actual_time` 差大 → 先标脚本差异

### 4.5 共性：滑动步作业步骤（逐步执行）

对每个滑动业务步 `[t0, t1)`（**每步单独写用时**）：

1. **写出** `step_name` / `sub_step` / `[t0,t1)` / `actual_time` / `op_kind`
2. **对齐电流**：取重叠 `diff_segments` + `spike_windows`，判断平台+尖峰是否符合 §4.2
3. **对齐 CPU**：取 `cpu_in_segment` Top；沙箱高则找同时段宿主（KI-001）
4. **拆段对比**：同一 suffix 多段滑动时逐步写，勿合并成「整段滑动」
5. **结论**：写清宿主包 + 行为（解码/预取/广告/渲染）；禁止只报沙箱名

| [§6.6 文档浏览](#66-云文档浏览document-browse) | `滑动查看文档` | 打开文件、云同步（§6.6） |

### 6.1 主页 / 应用界面待机（app-idle-home）

**典型场景**：GCash 主页待机、Grab 主页待机  
**行为特征**：App 前台亮屏，几乎无滑动/点击  
**排除**：Feed 滑动 → §6.2；灭屏长待机 → standby 流程

**分析侧重点**

| 优先级 | 查什么 |
|--------|--------|
| P0 | 待机步内：底电平台高且尖峰稀疏 → 常驻；密尖峰 → 心跳/定位 |
| P0 | Top 进程是否为业务主进程 / 关联沙箱（KI-001） |
| P0 | wakelock / Alarm / JobScheduler / FGS |
| P1 | GPS/FLP、推送长连接；首页动画/广告轮播 |
| P2 | 心跳周期是否密于低功耗版 |

**Log / 数据锚点**：`WakeLock`、`AlarmManager`、`JobScheduler`、`FusedLocation`；包名如 `gcash`、`grab`

**作业步骤**

1. 写出 YAML 逐步用时，标出业务待机步
2. 对齐该步电流：平台 vs 周期尖峰
3. 对比高低版主进程 CPU、wakelock
4. 结论区分：常驻负载 vs 周期唤醒，给出包名+进程名

**结论要点**：现象 Δ；主因进程；机制（常驻/心跳/定位/推送/动画）；建议验证

**下载段专属侧重点**

| 优先级 | 查什么 |
|--------|--------|
| P0 | 下载时段与电流抬升是否对齐；Play/`vending` CPU |
| P1 | 安装 `installd` |

**作业步骤**

1. **上下滑动步：按 §4.5 执行**

3. 下载证据弱但电流高 → 回看 §4 滑动/预加载段
