# SPD 配置核对（Android 工程）

## 文档角色（重要）

| 角色 | 含义 | 在本流程中的位置 |
|------|------|------------------|
| **SPD** | **检查项与规格**：要核对哪些配置/开关/资源、期望值、强制或推荐、生效 SKU/地区等 | **唯一依据**：可执行检查表必须从 SPD **展开**；不得用猜测替代 SPD 条款 |
| **工程树** | 实际 `prop` / `mk` / overlay / manifest 等 | **证据**：每条 SPD 检查项都应对应可引用的路径与摘录 |

**区分**：流程说明类文档**不是**检查项主表；检查行只能来自 **SPD**（条款、表格或清单），不能把任意说明文档误当成 SPD 逐条照抄。

## 文档类型说明

本 Skill 面向 **「条目在 SPD、证据在工程」** 的配置核对（非纯 log 排障）。  
**关键字**：工程内检索用语 + SPD 中出现的键名/路径模式；**分析步骤**：先锁定 SPD 与范围，再列项、取证、分级、出报告。

## 适用范围

- **问题类型**：工程配置是否与 **SPD** 要求一致（齐全性、取值、条件项是否触发等）。
- **适用场景**：交付 / MR / 多 SKU 分支合并前逐项核对；需要可追溯的「**SPD 条款 ↔ 证据**」矩阵。
- **适用平台**：以 Android 工程为主；平台与范围以 **SPD** 原文为准。

## 前置条件（输入）

| 输入 | 必需性 | 用途 |
|------|--------|------|
| **SPD** 或可追溯的条款表 | 必需 | **检查项**与期望值的唯一依据；无 SPD 则不得编造检查行 |
| 检查范围（分支、SKU、模块路径等） | 必需 | 「不适用」与取证边界 |
| 工程访问路径或仓库 | 必需 | 为每条 SPD 相关项收集证据摘录 |

**获取 SPD**：由用户指定链接、版本、章节或仓库内条款表；若项目另有「SPD 引用方式」，从其规定。

## 问题有效性确认

- **SPD** 版本 / 章节与任务一致。  （可选，若无版本无需判断）
- 判定边界（强制 / 推荐 / 条件）以 **SPD** 为准；披露方式（如何在报告中区分）按本 Skill 第五节默认集，除非用户或项目另有模板。

## 分析工作流

### 总览

1. **步骤 0**：确认输入、理解本 Skill 的输出结构与边界（不把非 SPD 文档误当检查表）。  
2. **步骤 1**：锁定 **SPD**、检查范围及元信息（版本、分支、SKU）。  
3. **步骤 2**：将 **SPD** 展开为「一条检查项一行」的可执行表（ID 建议用 SPD 条款/表行）。  
4. **步骤 3**：在工程内按合理顺序收集证据（路径 + 摘录）。  
5. **步骤 4**：按默认结论集对照 **SPD** 要求分级。  
6. **步骤 5**：按下文「输出格式」生成报告（矩阵主键为 **SPD 条目**）。

更细的子步骤与判断表见 [ANALYSIS_STEPS.md](ANALYSIS_STEPS.md)。

### 步骤 0：确认输入与流程边界

**目标**：明确本次必须产出可追溯矩阵；检查项**只**来自 SPD。

**操作**：

1. 确认已具备：SPD（或条款表）、检查范围、工程路径。  
2. 明确：**不得**把流程说明/会议纪要等非 SPD 正文当成检查项清单。

**若不满足**：缺 SPD 则停止列检查行，只列出需要用户补充的 SPD 信息。

### 步骤 1：锁定 SPD 与检查范围

**目标**：固定 SPD 版本与本次分支/SKU/模块边界。

**操作**：

1. 记录 SPD 来源、版本、章节（若有）。  
2. 写明检查范围：分支、机型/SKU、模块目录、debug/release、MR 涉及文件列表等。  
3. 从 **SPD** 识别强制 / 推荐 / 条件项及生效条件。

### 步骤 2：从 SPD 生成可执行检查项表

**目标**：**一行 = SPD 的一条检查要求**（表格行、条款或清单项）。

建议列结构：

| 检查 ID | SPD 原文/序号/条款 ID | 类型（强制/推荐/条件） | 生效条件 | 期望配置摘要 | 建议取证位置（若 SPD 有写） |
|---------|------------------------|------------------------|----------|--------------|---------------------------|

**原则**：子条款单独成行；条件项写清触发条件；**禁止**在无 SPD 依据时增加行。

### 步骤 2.1：专项范围（仅提取以下四类）

本次仅从 SPD 提取并维护以下专项的检查项：

- **万能播放引擎**
- **视频 HDR**
- **画质增强**
- **视频省电**

除上述四类外，其他 SPD 条目暂不纳入本次执行矩阵。

### 四类专项检查项（从 SPD 提取）

> 说明：以下“检查方法”来自你提供的现行检查口径；`SPD 原文/条款 ID` 仍需在执行时补齐为可追溯条款。

| 分组 | 检查 ID（建议） | SPD 原文/条款 ID | 检查方法（明确执行命令/动作） | 判定规则（当前口径） | 不满足时导入方法（按当前规则） | 证据要求 |
|------|------------------|------------------|----------------------------------|----------------------|--------------------------------|----------|
| 万能播放引擎 | UPE-01 | [从 SPD 填写] | 使用 ADB 主动执行：1) 优先查询 `/sdcard/` 下可播放视频（例如 `adb shell "ls /sdcard/*.mp4 2>/dev/null"`，必要时再补查 `/sdcard/Movies`、`/sdcard/DCIM/Camera`）；2) 若设备无可播视频，从 `\\10.205.4.20\sw_log\多媒体Log\xieyu\Video稳定性挂测\1支持万能引擎\TC_10000` 选择视频文件（优先 `.mp4`）并导入设备 `/sdcard/`（示例：`adb push \\10.205.4.20\sw_log\多媒体Log\xieyu\Video稳定性挂测\1支持万能引擎\TC_10000\xxx.mp4 /sdcard/`）；3) 使用显式组件启动播放器（示例：`adb shell am start -n com.transsion.magicshow/com.transsion.magicvideo.activities.VideoPlayerActivity -a android.intent.action.VIEW -d "file:///sdcard/xxx.mp4" -t "video/mp4"`）；4) 播放后抓日志并搜索 `TranMediaPlayer`；5) 检查结束后关闭播放界面（示例：`adb shell am force-stop com.transsion.magicshow`） | 搜到 `TranMediaPlayer` 视为支持；未搜到视为不支持/待确认 | 依赖 visha 专项导入；不需要修改代码。若未导入，记录为“未导入”，并在最终输出中提出 | 保留设备侧文件查询输出、视频源路径与 `adb push` 输出、启动命令、播放器截图或步骤说明 + 关键日志摘录 + 关闭播放界面命令 |
| 视频 HDR | HDR-01 | [从 SPD 填写] | 执行 `adb shell getprop ro.vendor.mtk_hdr_video_support` | 值为 `1` 视为支持；其他值视为不支持 | 平台限制：平台支持则默认导入；具体参照支持表“视频HDR平台能力” | 保留命令与原始输出 + 平台能力判定依据 |
| 画质增强 | PQE-01 | [从 SPD 填写] | 执行 `adb shell getprop ro.tr_video.vee.support` | 值为 `1` 视为支持；其他值视为不支持 | 平台限制：D8300 及以上支持；未完成时需做移植 | 保留命令与原始输出 + 平台型号信息 |
| 视频省电 | PWR-01 | [从 SPD 填写] | 执行 `adb shell getprop ro.tr_media.smartmediaengine.feature.support` | 值为 `1` 视为支持；其他值视为不支持 | NA | 保留命令与原始输出 |

补充要求：

1. 若命令输出为空、属性不存在或设备无 ADB 权限，结论标记为“证据不足”，不得直接判“已满足”。  
2. 若 SPD 对某项有更严格阈值或前置条件（如机型/SKU/区域限制），以 SPD 原文覆盖上述默认口径。  
3. 报告矩阵中必须同时写入：`SPD 条款 ID`、`检查命令/动作`、`原始输出或日志摘录`、`不满足时导入动作`。

### 步骤 4.1：不满足项导入处理（必须执行）

在步骤 4 得到分级后，按以下规则处理“不满足”项：

1. **满足项**：标记 `Pass`，无需导入动作。  
2. **不满足项**：按“四类专项检查项”表中的“导入方法”执行对应处理，并记录状态（已导入/待导入/NA）。  
3. **无法立即导入**：必须在最终报告中单列“待导入项与阻塞原因”。

### 步骤 3：从工程收集证据

**目标**：为每个 **SPD 检查 ID** 取得 **路径 + 摘录**。

**操作**：

1. 搜索、读文件或脚本输出；可按模块/目录顺序，保证强制项优先。  
2. 每个 SPD 检查 ID 至少尝试一条证据；可读多文件。  
3. 未读到的文件 **不得** 推断为已满足。

### 步骤 4：逐项对照并分级

**目标**：对每个 **SPD 检查 ID** 给出结论标签。

**默认结论集**（项目可约定替换用语，但含义应一致）：

- **已满足**：证据充分且符合 **SPD** 要求。  
- **缺失**：**SPD** 要求明确但工程未体现或明显不符。  
- **歧义**：**SPD** 或实现有多种合理解释，需产品/配置确认。  
- **不适用**：写明 NA 理由（如当前范围不含该 SKU）。  
- **多余（可选）**：仅在用户要求清理时，报告与现行 **SPD** 冲突的遗留项。

### 步骤 5：输出报告

**目标**：报告含元信息、过程摘要、**以 SPD 检查 ID 为主键的执行矩阵**。

证据写法示例见 [ANALYSIS_STEPS.md](ANALYSIS_STEPS.md) 文末。

## 注意事项

- **条目跟 SPD**：检查行必须能追溯到 SPD；不得用非 SPD 文档顶替检查表。  
- **无 SPD 则停**：不得列出无条款依据的具体检查项。  
- **证据不足 ≠ 通过**：未读到的文件不得推断为已满足。  
- **敏感信息**：摘录中隐去密钥、token。
