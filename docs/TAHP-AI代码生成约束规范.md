# TAHP AI代码生成约束规范

> **版本**: v2.0 | **日期**: 2026-05-19 | **适用范围**: 所有AI Agent在TAHP系统中执行代码生成/修改任务
> **状态**: Approved | **优先级**: P0
> **v2.0 变更**: 适配知识库体系 — AI执行时自动检索相关知识注入上下文，执行完成后自动沉淀经验到知识库

---

## 0. 总纲

本规范是TAHP系统中所有AI Agent执行代码生成、代码修改、Bug分析代码产出等任务的**强制性约束**。违反本规范的产出将被质量门禁自动拒绝。

### 核心原则

```
1. 不跑偏  — 严格在约束文件定义的scope内操作
2. 不幻觉  — 所有代码产出必须有据可查，禁止编造
3. 不反复  — 一次性产出正确代码，不接受迭代试错
4. 严格规范 — 严格按照约束文档执行，不擅自放宽标准
5. 有知识  — 执行任务前检索知识库获取相关经验，执行后沉淀新知识（v3.0）
```

## 1. 信息边界约束（防跑偏）

### 1.1 Scope锁定规则

AI Agent在执行任务前，**必须**先执行以下步骤：

```
Step 0: 检索知识库（v3.0 新增）
  - 调用 query_knowledge.py 检索与当前任务相关的经验案例和错误模式
  - 将 Top-K 相关知识注入 Agent 上下文
  - 跨模块任务需额外检索 shared/ 中的通用知识
  - 如果知识库为空或无匹配结果，记录日志并继续执行（不阻塞）

Step 1: 读取模块约束文件
  → 加载 constraints/{module}/module.yaml
  → 解析 scope.includes 和 scope.excludes

Step 2: 锁定操作范围
  → 只操作 scope.includes 中列出的路径
  → 任何对 scope.excludes 中路径的读写操作都被禁止
  → 跨模块操作必须显式加载目标模块的约束文件

Step 3: 确认依赖
  → 读取 scope.dependencies
  → 如果涉及依赖模块，加载其约束文件作为参考
  → 不自行推断模块间的依赖关系

Step 4: 范围声明
  → 在开始分析/修改前，输出范围声明：
    "[SCOPE] 本任务操作范围: {module} 模块, 涉及路径: {paths}"
  → 任何超出此范围的代码操作都是违规
```

### 1.2 Scope违规检测

| 违规类型 | 检测方式 | 处理 |
|---------|---------|------|
| 读取排除区域文件 | 路径匹配 `scope.excludes` | 警告并跳过 |
| 修改排除区域文件 | 路径匹配 `scope.excludes` | **立即停止，报告违规** |
| 修改非include路径文件 | 路径不在 `scope.includes` 中 | **立即停止，请求确认** |
| 跨模块操作未加载约束 | 操作目标不在当前module约束中 | **立即停止，加载目标约束** |

### 1.3 信息获取边界

```
允许的信息来源:
  ✓ constraints/ 目录下的约束文件
  ✓ scope.includes 中定义的代码路径
  ✓ eval-data/ 目录下的评估案例
  ✓ skills/ 目录下已验证的Skill
  ✓ MCP工具返回的结构化数据

禁止的信息来源（防幻觉）:
  ✗ 编造不存在的API/方法/类名
  ✗ 推断未在代码中验证的行为
  ✗ 假设特定的Modem/芯片行为（除非有日志证据）
  ✗ 引用未在约束文件或代码中出现的文档
```

## 2. 防幻觉规则（Anti-Hallucination）

### 2.1 代码生成防幻觉

#### 规则 A: 真实性验证

AI生成的每一行代码修改**必须**满足以下至少一条：

| # | 验证条件 | 说明 |
|---|---------|------|
| 1 | **已有代码引用** | 引用的类/方法/变量在当前代码库中存在（通过grep验证） |
| 2 | **约束文件授权** | 约束文件中明确列出的API/方法/路径 |
| 3 | **Android SDK文档** | 引用Android官方SDK文档中的API（需注明来源版本） |
| 4 | **MCP工具确认** | 通过MCP工具查询并确认的接口/配置 |

**不满足任何一条的代码 = 幻觉代码 = 禁止输出**

#### 规则 B: 禁止推断模式

以下推断模式被**严格禁止**：

```
禁止:
  ✗ "根据经验，这个方法应该是xxx"          → 没有代码证据
  ✗ "类似的模块是这样实现的，这里也应该"     → 没有验证当前模块
  ✗ "这个参数通常传入xxx"                  → 没有调用点证据
  ✗ "这个类应该继承自xxx"                  → 没有类层次证据
  ✗ "Modem通常返回这个错误码"              → 没有日志证据

正确做法:
  ✓ "grep确认 ClassA.methodB() 存在于 frameworks/opt/telephony/"
  ✓ "约束文件 bug-analysis.yaml 第45行指定了此处理方式"
  ✓ "logcat日志第1234行显示: 'RILJ: RIL_REQUEST_* error=xxx'"
  ✓ "Android 14 API Reference: TelephonyManager类具有此方法"
```

#### 规则 C: 未知即报告

当AI无法确认某个代码行为或API存在性时：

```
正确响应模板:
"[UNCERTAIN] 无法确认 {具体内容}，原因: {具体原因}。
 建议: {具体建议}
 风险: {如果忽略此不确定性的潜在风险}"
```

**禁止**: 在不确定的情况下仍然生成代码并标注"可能需要调整"。

### 2.2 Bug分析防幻觉

#### 规则 D: 基于证据的根因判定

```
根因判定证据链要求:

Level 1 (强证据):
  ✓ logcat中直接显示的异常堆栈
  ✓ 代码中明确的逻辑错误（可指出具体文件:行号）
  ✓ Modem返回的错误码与已知错误码表匹配

Level 2 (中等证据):
  ✓ 日志中的异常模式（时间序列分析）
  ✓ 代码路径分析推导的异常流程
  ✓ 与已知Bug pattern匹配

Level 3 (弱证据):
  △ 经验推断（必须标注为"推测"）
  △ 与其他平台行为类比（必须标注为"参考"）

规则:
  - 根因判定必须基于 Level 1 或 Level 2 证据
  - 仅基于 Level 3 证据的判定必须输出 "[SPECULATIVE]" 标签
  - 不允许无证据的根因判定
```

#### 规则 E: 日志解析防幻觉

```
日志引用规则:
  ✓ 引用日志时必须附带原始行（或行号范围）
  ✓ 不允许转述/改写日志内容
  ✓ 不允许省略日志中的关键上下文
  ✓ 如果日志内容不完整，必须声明 "[INCOMPLETE_LOG]"
```

### 2.3 修复方案防幻觉

#### 规则 F: 修复方案约束

```
修复代码产出前必须通过以下检查:

[ ] 方案与根因一致（不是治标不治本）
[ ] 修改文件在 scope.includes 范围内
[ ] 修改不超过必要的最小范围（最小化变更原则）
[ ] 新增代码遵循模块编码规范
[ ] 不引入新的编译警告
[ ] 不影响排除范围内的代码
[ ] 不破坏已有的错误处理逻辑
[ ] 如果涉及接口变更，同时更新HIDL/AIDL定义
```

## 3. 一次性正确规则（防反复修改）

### 3.1 修改协议

AI Agent执行代码修改时**必须**遵循以下协议：

#### Phase 1: 分析（只读，禁止修改任何文件）

```
[ANALYSIS PHASE]
1. 读取相关约束文件
2. 搜索代码库，确认目标代码的位置和当前状态
3. 理解代码上下文（调用关系、数据流、依赖关系）
4. 列出所有需要修改的文件和具体修改点
5. 验证每个修改点的正确性（引用规则A的证据）
6. 输出修改计划:

[MODIFICATION PLAN]
目标: {一句话描述}
修改文件列表:
  1. {file_path}
     - 修改类型: {add/modify/delete}
     - 修改位置: {class.method} 或 {行号范围}
     - 修改原因: {具体原因}
     - 影响范围: {受影响的调用方}
  2. ...
风险评估:
  - 编译影响: {是否会引入编译问题}
  - 运行时影响: {是否影响现有功能}
  - 回归风险: {可能的回归场景}

等待确认后进入Phase 2。
```

#### Phase 2: 修改（严格按计划执行）

```
[MODIFICATION PHASE]
规则:
  - 严格按照Phase 1的修改计划执行
  - 不擅自增加新的修改点
  - 如果发现计划中的修改有问题，停止修改，返回Phase 1
  - 每个文件修改后，立即输出diff摘要
  - 修改完成后，列出所有变更

[MODIFICATION SUMMARY]
变更文件数: {N}
新增行数: {N}
删除行数: {N}
修改行数: {N}
```

#### Phase 3: 验证（修改后必须执行）

```
[VERIFICATION PHASE]
自动检查（MCP工具执行）:
  [ ] 编译检查: {编译命令和结果}
  [ ] Lint检查: {checkpatch/lint结果}
  [ ] 单元测试: {测试结果（如有）}
  [ ] 代码diff审查: {最终diff}

手动审查项:
  [ ] 修改是否与根因一致
  [ ] 是否有遗漏的修改点
  [ ] 是否有超出scope的修改
  [ ] 编码风格是否合规
```

### 3.2 禁止模式

以下模式被**严格禁止**：

```
禁止的交互模式:
  ✗ "我先改一下试试看"            → 不允许无计划的试错修改
  ✗ "可能需要再调一下"             → 必须在Phase 1就确定正确方案
  ✗ "这个改法应该可以，你测试一下"  → AI必须自己验证，不能推给人类测试
  ✗ "另一个方案可能是..."          → 只给出一个最优方案，不给选择题
  ✗ 修改 → 发现问题 → 再修改 → 再发现...  → 必须在Phase 1分析透彻后一次性修改

正确的交互模式:
  ✓ 完整分析 → 输出计划 → 等待确认 → 一次性修改 → 自验证 → 交付
```

### 3.3 最小化变更原则

```
变更最小化规则:
  - 只修改与Bug直接相关的代码
  - 不做"顺便优化"或"顺便重构"
  - 不修改格式/注释（除非是bug原因）
  - 不添加"防御性代码"（除非约束文件要求）
  - 保持现有代码风格一致

例外:
  - 约束文件明确要求的改进可以同时进行
  - 安全红线要求的安全加固必须同时进行
```

## 4. 错误处理与恢复

### 4.1 错误分类与响应

| 错误类型 | 响应方式 |
|---------|---------|
| **Scope违规** | 立即停止操作，报告违规详情，等待人工决策 |
| **幻觉检测** | 撤回幻觉产出，标注不确定内容，请求人工确认 |
| **编译失败** | 分析编译错误，判断是否在scope内，修复后重试一次，若仍失败则报告 |
| **测试失败** | 分析失败原因，区分是测试本身问题还是修改问题，给出明确判断 |
| **约束冲突** | 报告冲突的约束条目，建议人工仲裁 |

### 4.2 回滚机制

```
回滚触发条件:
  - 修改后编译失败且无法在scope内修复
  - 发现修改超出了Phase 1计划的scope
  - 质量门禁检查不通过

回滚执行:
  1. 使用git checkout恢复所有修改文件
  2. 清理所有新生成的临时文件
  3. 输出回滚报告，说明回滚原因
  4. 保留分析结果供后续参考
```

## 6. 强制检查清单

### 代码修改前必检

- [ ] 已读取并理解目标模块约束文件
- [ ] 已确认所有修改文件在scope.includes范围内
- [ ] 已确认不涉及scope.excludes中的任何路径
- [ ] 已确认所有引用的API/方法在代码库中真实存在
- [ ] 已完成Phase 1分析并输出修改计划
- [ ] 修改计划已获得确认（如需确认）

### 代码修改后必检

- [ ] 所有修改严格按Phase 1计划执行
- [ ] 未引入超出计划的额外修改
- [ ] 编译通过（或已知编译问题已在scope外）
- [ ] 代码风格符合模块编码规范
- [ ] 不存在"TODO"/"FIXME"未关联Bug ID
- [ ] 涉及接口变更时已同步更新接口定义
- [ ] 输出格式符合第5节规范

## 7. 违规处理

| 违规级别 | 处理方式 |
|---------|---------|
| **P0 - Scope违规** | 立即停止所有操作，标记任务为BLOCKED，通知人工 |
| **P0 - 安全红线违规** | 立即停止，标记为CRITICAL，通知安全负责人 |
| **P1 - 幻觉代码产出** | 撤回产出，重新分析，累计3次则降级评估 |
| **P1 - 未经计划的修改** | 撤回修改，返回Phase 1重新分析 |
| **P2 - 格式不规范** | 要求修正格式后重新提交 |
| **P2 - 不完整输出** | 要求补充缺失的分析维度 |

## 8. 知识库交互规范 (v3.0 新增)

### 8.1 知识检索规则

AI Agent 执行任何代码生成/修改任务前，**必须**执行知识检索：

```
执行流程（v3.0）:
  Step 0: 检索知识库 → 获取相关经验和错误模式
  Step 1: 读取约束文件 → 锁定 Scope
  Step 2: 分析任务 → 制定方案
  Step 3: 代码生成 → 遵循规范
  Step 4: 自检验证 → 确保质量
  Step 5: 知识沉淀 → 记录经验（新增）
```

### 8.2 知识注入规范

- **注入时机**: 在读取约束文件之后、制定方案之前
- **注入内容**:
  - 模块专属经验案例（Top-5）
  - 相关错误模式（Top-3）
  - 跨模块共享知识（如适用，Top-3）
- **注入方式**: 作为上下文的一部分提供给 Agent，不影响约束文件的权威性
- **优先级**: 约束文件 > 知识库经验 > Agent 默认行为

### 8.3 知识沉淀规范

AI Agent 执行完以下任务后，**必须**沉淀经验到知识库：

| 触发场景 | 沉淀内容 | 沉淀条件 |
|---------|---------|---------|
| Bug 分析完成 | 分析案例（根因、关键日志、修复建议） | 质量门禁 P1/P2 通过 |
| 代码修改完成 | 修改记录（改了什么、为什么改） | 编译通过 |
| 错误被纠正 | 纠正案例（原始输出 vs 正确结果） | 始终沉淀 |
| 适配任务完成 | 适配经验（成功模式、踩坑记录） | 编译+回归通过 |

### 8.4 知识库操作接口

```bash
# 检索知识
python scripts/query_knowledge.py --module {module} --query "{task_description}"

# 沉淀经验（通常由系统自动调用）
python scripts/feed_knowledge.py --module {module} --cases ./auto-generated/case-{id}.md

# 查看知识库状态
python scripts/query_knowledge.py --module {module} --stats
```

### 8.5 知识置信度处理

知识库中的条目有置信度评分（0.0-1.0），AI Agent 应：

- **高置信度 (≥0.8)**: 直接参考，作为强指导
- **中置信度 (0.6-0.8)**: 参考但需结合约束文件验证
- **低置信度 (<0.6)**: 仅作参考，不作为决策依据
- **无置信度**: 来自 Owner 手动投喂的知识，默认为高置信度
