# TAHP 评估指标体系

> **版本**: v1.0 | **日期**: 2026-05-18 | **状态**: Approved
>
> 配套文档: [TAHP-评估与质量门禁规范](../../TAHP-评估与质量门禁规范.md)
>
> 本文档定义 TAHP 系统中 AI 输出的质量评估指标、评估流程和质量门禁规则。

---

## 1. 评估目标

确保 AI 输出质量达到**可发布标准**，通过量化指标驱动 Skill 持续进化。

核心原则：

```
1. 评估不是为了给 AI 打分，而是为了持续提升系统对开发者的价值
2. 评估数据驱动约束文件的优化和 Skill 的进化
3. 所有指标必须可自动化度量，减少人为判断
```

---

## 2. 三级策略定义

TAHP 对 AI 输出采用三级策略分类，决定产出是否可直接发布：

| 策略 | 判定条件 | 处理方式 | 人工介入 |
|------|---------|---------|---------|
| **全自动** | 综合置信度 > 95% | 自动通过，直接发布 | 无需 |
| **半自动** | 综合置信度 70-95% | 需人工审核后发布 | 人工审核 |
| **人工** | 综合置信度 < 70% | 必须人工处理 | 全面人工 |

### 2.1 置信度评估维度

| 维度 | 权重 | 说明 |
|------|------|------|
| API 迁移规则匹配度 | 40% | 规则库中是否有完全匹配的迁移规则 |
| 代码变更复杂度 | 20% | 涉及文件数、改动行数、连锁影响 |
| 上下文确定性 | 20% | 是否需要运行时判断、是否依赖设备状态 |
| 历史成功率 | 15% | 类似迁移模式的历史成功率 |
| 测试覆盖度 | 5% | 是否有对应测试用例可验证 |

### 2.2 策略阈值说明

- **不建议将全自动阈值降到 90% 以下**，全自动适配缺乏人工审核环节，过低的阈值会引入质量风险
- Owner 可在约束文件中通过 `strategy_preferences` 自定义阈值

## 3. 核心评估指标

### 3.1 Skill 质量指标

| 指标 | 权重 | 计算方式 | 目标值 | 说明 |
|------|------|---------|--------|------|
| **准确率 (Accuracy)** | 40% | 正确案例数 / 总案例数 | >= 85% | 分析结果与实际根因的匹配度 |
| **完整性 (Completeness)** | 20% | 必填字段填写率 | 100% | 覆盖所有必要分析维度 |
| **一致性 (Consistency)** | 15% | 相同输入产出一致率 | >= 90% | 相同输入多次执行的结果稳定性 |
| **时效性 (Efficiency)** | 15% | 平均完成时间 | <= 5min/案例 | 单个案例平均处理时间 |
| **可解释性 (Explainability)** | 10% | 证据引用率 | >= 80% | 分析结论有日志/代码证据支撑的比例 |

### 3.2 指标详细定义

#### 准确率 (Accuracy)

分析结果与实际根因的匹配程度，是最核心的指标。

```
计算方式:
  accuracy = 正确案例数 / 总测试案例数

判定标准（以 bug_analysis 为例）:
  - root_cause_layer 与期望一致
  - severity 允许偏差 1 级
  - fix_type 与期望一致
  - root_cause_description 包含期望的关键词

门禁:
  >= 85%: PASS
  70-84%: WARNING（允许上线但需改进）
  < 70%: FAIL（不允许上线）
```

#### 完整性 (Completeness)

产出是否覆盖了所有必要的分析维度。

```
计算方式:
  completeness = 已填写的必填字段数 / 必填字段总数

必填维度（bug_analysis）:
  - root_cause_layer
  - reproducibility
  - impact_scope
  - fix_type
  - severity
  - root_cause_description (>= 50 字)
  - fix_suggestion (>= 30 字)

目标: 100%（所有必填维度必须覆盖）
```

#### 安全性 (Safety)

安全红线违反率，属于一票否决指标。

```
计算方式:
  safety_violation_rate = 安全红线违反次数 / 总执行次数

门禁:
  0 次违反: PASS
  >= 1 次违反: BLOCK（立即停止，通知安全负责人）

安全红线清单（参见 TAHP-评估与质量门禁规范 §10.2）:
  - 不允许新增危险权限申请
  - 不允许硬编码密钥、Token、证书
  - 不允许绕过加密/签名验证
  - 不允许使用不安全协议
  - 不允许动态加载未签名文件
```

#### 可执行性 (Actionability)

输出方案可直接落地、无需额外人工修改的比例。

```
计算方式:
  actionability = 可直接执行的方案数 / 总方案数

可执行判定标准:
  - 代码 Patch 可编译通过
  - 修改文件在 scope.includes 范围内
  - 不违反任何约束红线
  - 编码风格符合模块规范

目标:
  诊断引擎: >= 80%
  适配引擎（全自动项）: 100%
  适配引擎（半自动项）: >= 70%
```

#### 一致性 (Consistency)

相同输入多次执行的结果稳定性。

```
计算方式:
  consistency = 产出一致的执行次数 / 总执行次数（同一输入执行 N 次，N >= 5）

目标: >= 90%

注意:
  一致性不要求输出完全相同（如描述措辞），但核心结论必须一致:
  - root_cause_layer 一致
  - severity 一致（允许偏差 1 级）
  - fix_type 一致
  - 修改文件列表一致
```

## 4. 评估流程

### 4.1 流程概览

```
Step 1: 测试用例准备
  └─ eval-data/{module}/cases/ 目录下的 YAML 文件

Step 2: 预期结果定义
  └─ eval-data/{module}/expected/ 目录下的 JSON 文件

Step 3: 自动执行 + 对比
  └─ python scripts/evaluate.py --module {module} --split test

Step 4: 指标计算
  └─ 自动计算 accuracy / completeness / consistency / efficiency / explainability

Step 5: 报告生成
  └─ reports/ 目录下生成 Markdown 格式评估报告
```

### 4.2 测试数据集规范

```
eval-data/{module}/
├── train/                    # 训练/进化集（60%）
├── val/                      # 验证集（20%）
└── test/                     # 测试集（20%）
```

| 要求 | 标准 |
|------|------|
| 最小案例数 | 每模块 >= 15 个（train 9 / val 3 / test 3），初期 >= 5 个 |
| 案例真实性 | 必须来自真实 Bug/问题，不允许虚构 |
| 难度分布 | easy:medium:hard ≈ 3:5:2 |
| 时间分布 | 覆盖近 6 个月的不同版本 |

### 4.3 评估命令

```bash
# 运行单个模块评估
python scripts/evaluate.py --module telephony --split test

# 运行全部模块评估
python scripts/evaluate.py --all-modules

# 检查质量门禁
python scripts/gate-check.py --module telephony --level P0
```

## 5. 质量门禁规则

### 5.1 三级门禁

#### P0 (BLOCK) — 安全与致命错误

任一失败即阻止，不允许继续：

| # | 检查项 | 工具 | 标准 |
|---|--------|------|------|
| 1 | 编译检查 | Android build system | 零 error |
| 2 | Scope 合规 | 路径匹配约束文件 | 零违规 |
| 3 | 安全红线 | 自定义检查规则 | 零违规 |
| 4 | API 真实性 | grep + API 索引 | 零幻觉 |

#### P1 (WARNING) — 质量警告

累计超过阈值则警告：

| # | 检查项 | 工具 | 标准 |
|---|--------|------|------|
| 5 | 编码风格 | checkpatch.pl / clang-format | 零 warning |
| 6 | 新增 Lint 错误 | Android Lint | 零新增 |
| 7 | 废弃 API 使用 | @Deprecated 扫描 | 零使用 |
| 8 | TODO 关联 | 正则匹配 Bug ID | 100% 关联 |

#### P2 (RECORD) — 记录但不阻止

| # | 检查项 | 工具 | 标准 |
|---|--------|------|------|
| 9 | 代码复杂度 | 圈复杂度分析 | 单方法 <= 15 |
| 10 | 重复代码 | PMD/CPD | <= 3% |
| 11 | 注释覆盖率 | 注释行/代码行 | 公开 API >= 80% |

### 5.2 门禁判定逻辑

```
P0 全通过 + P1 <= 2 项超标 → PASS
P0 任一失败              → BLOCK
P1 > 2 项超标            → WARNING
P2 任意数量              → RECORD（记录即可）
```

## 6. 进化评估指标

### 6.1 EvoSkill 进化效果度量

| 指标 | 计算方式 | 基线参考 |
|------|---------|---------|
| **准确率提升** | 新 Skill 准确率 - 基线准确率 | 目标: >= +10pp |
| **泛化能力** | 跨任务测试集准确率 | 目标: >= +5pp |
| **进化效率** | 达到目标准确率的迭代次数 | 目标: <= 10 轮 |
| **Frontier 收敛速度** | 连续无改进轮数 | 停止阈值: 5 轮 |

### 6.2 迭代改进率

```
improvement_rate = (当前轮准确率 - 上一轮准确率) / 上一轮准确率

监控规则:
  - improvement_rate > 0: 正常进化
  - improvement_rate 连续 5 轮 <= 0: 终止进化，保留当前 Frontier 最优
  - accuracy 下降超过 5pp: 暂停进化，人工检查约束文件
```

### 6.3 Frontier 收敛速度

```
Frontier 维护规则:
  - 保留最多 N 个 Skill 变体（默认 N=3）
  - 新 Skill 必须在至少一个维度优于已有 Skill 才能入替
  - 被替换的 Skill 保留在 archive/，不删除
  - 每次替换记录原因和对比数据

收敛判断:
  - 连续 5 轮无新的 Skill 进入 Frontier → 收敛
  - 进化超过 20 轮仍未达标 → 终止，输出分析报告
```

## 7. 持续改进机制

### 7.1 反馈闭环

```
开发者使用 Skill → 发现问题 → 提交反馈
                                     │
                                     ↓
                           系统记录反馈
                                     │
                           ┌─────────┤
                           ↓         ↓
                     约束不足?   Skill 不足?
                           ↓         ↓
                     更新约束文件  启动进化循环
                           ↓         ↓
                     通知 Owner  自动优化 Skill
                           ↓         ↓
                           └──→ 合并 ←──┘
                                   │
                                   ↓
                           更新版本，重新评估
```

### 7.2 定期评审

| 评审类型 | 频率 | 参与人 | 内容 |
|---------|------|--------|------|
| 约束文件评审 | 每月 | Owner + TL | 审查约束完整性、准确性 |
| Skill 质量评审 | 每月 | TL + 开发者代表 | 审查 Skill 效果、用户反馈 |
| 系统效果评审 | 每季度 | 部门经理 + TL | 审查整体 ROI、决定资源投入 |
| 安全评审 | 每季度 | 安全负责人 | 审查安全红线、权限管理 |

### 7.3 系统效果度量

| 指标 | 采集方式 | 目标 |
|------|---------|------|
| Bug 分析人力节省 | 时间日志对比 | >= 30% |
| 代码适配成功率 | 门禁记录 | >= 80% |
| Skill 复用率 | 引用计数 | >= 40% |
| Owner 月均投入 | 时间日志 | <= 4h/月 |
| False Positive 率 | 人工审核 | <= 15% |

### 7.4 版本管理

```
Skill 版本号: MAJOR.MINOR.PATCH

MAJOR: Skill 结构重大变更（评估方法变更）
MINOR: Skill 逻辑优化（准确率提升 >= 5pp）
PATCH: Skill 小修复（修复个别失败案例）

Git 分支策略:
  main       ← 稳定版本，通过所有门禁
  develop    ← 开发版本，正在进化的 Skill
  feature/*  ← 实验性功能
  archive/*  ← 被替换的旧版本
```
